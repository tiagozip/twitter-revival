# Twitter for Android 4.1.9 endpoints

The 4.1.9 routes live in `server/src/v11.js`. `server.js` sends every `/1.1/` request to `handleV11` inside `requestEra.run("2014", ...)`, and logs `UNHANDLED 1.1 <path>` and returns `{}` when no route claims it. `/1/`, `/i/` and `/mobile_client_api/` requests from a 4.x User-Agent, or with `X-Revival-Client: 2014`, also try `handleV11` first and then fall back to `handleV3` and `handleV1`. Most routes reuse the 2011 and 2012 handlers. The 2014 era flag makes `fixStatus` in `v1.js` add real `entities.media`, hashtags and `current_user_retweet` on top of the U+2060 `/m/` payload link that the older clients use.

Sources are jadx single-class decompiles of `apks/twitter-4.1.9.apk`. The request builders are in `com.twitter.library.api.TwitterService`, the parser dispatch is `api/ag` (by type id) and the parsers are in `api/ah`. The app builds URLs as `v.a(base, "1.1", ...)` and only accepts responses whose content type starts with `application/json`.

## Parser requirements

### Tweets

- `id` has to be a JSON number. `id_str` is ignored.
- `user` has to be present. A tweet without one throws NullUserException and the whole response fails.
- The parser reads `in_reply_to_status_id`, `in_reply_to_user_id`, `in_reply_to_screen_name`, `retweet_count`, `favorited`, `retweeted`, `created_at`, `text`, `source`, `retweeted_status` and `entities`. It never reads `favorite_count`, so the like count does not show anywhere.
- `current_user_retweet: {id}` turns the tweet into "retweeted by me", and the outer id becomes `current_user_retweet.id`. The server sets it to the tweet id plus one, which is the fake wrapper id that `statuses/destroy` already maps back to an unretweet.

### Entities

- `urls` read `url_https`, `url`, `expanded_url`, `display_url` and `indices`.
- `media` reads `id`, `url_https`, `media_url_https`, `media_url`, `type` (has to be `photo`), `sizes.large.w`, `sizes.large.h` and `features.large.faces`. The first media entity becomes the photo preview.
- `indices` are UTF-16 offsets. The app does no code point conversion, so the JS string offsets are already right.

### Users

- `id` has to be a number above 0, and `screen_name` has to be set. Otherwise the parser returns null and the row is dropped.
- It reads `following`, `followed_by`, `blocking`, `can_dm` and `notifications`. `created_at` can be a long or a date string.
- `entities.url` and `entities.description` are optional.

### `timeline/home`

```json
{"twitter_objects":{"tweets":{"<id>":tweet},"users":{"<id>":user}},
 "response":{"timeline":[{"tweet":{"id":"<id>"},"entity_id":{"ids":["<id>"]}}]}}
```

- `twitter_objects` has to come before `response`. The parser streams the JSON and resolves timeline entries against the maps it has already read.
- Ids inside `response.timeline` are strings.
- Every tweet's user has to be in `users`, including the user of a `retweeted_status`.
- An entry can also be `{conversation:{ids, context:{root_user_id, target_tweet_id, participant_ids, participants_count, target_count}}, entity_id}`. The server does not emit it.

### Activity

- The response is an array of objects, and `action` (or `event`) has to be the first key in each.
- `created_at` is a date string, and `max_position` and `min_position` are digit strings.
- Each action has a fixed set of fields:

  | action            | sources | targets  | target_objects |
  | ----------------- | ------- | -------- | -------------- |
  | favorite          | users   | statuses | none           |
  | mention           | users   | users    | statuses       |
  | reply             | users   | statuses | statuses       |
  | retweet           | users   | statuses | statuses       |
  | follow            | users   | users    | none           |
  | list_member_added | users   | users    | lists          |
  | list_created      | users   | lists    | none           |

- `activity/about_me/unread` reads the first integer field it finds. With no number in the object it throws a NullPointerException, so the server always returns `{"cursor":<number>}`.

### Cursored lists

- Users, lists and ids responses need `next_cursor_str` as a string. `"0"` means there is no next page.

### `search/universal` and `discover/universal`

- The response needs a `modules` array, and the parser throws when it is missing. Each module is a one-key object: `status`, `user`, `news`, `suggestion`, `user_gallery`, `media_gallery`, `tweet_gallery` or, on discover, `wtf`.
- Inside a module, `metadata` has to come before `data`.
- Search pages with `next_cursor=` or `prev_cursor=` and reads `metadata.cursor`. People search sends `modules=user`, photo search sends `modules=tweet&filter=images`, and realtime search sends `result_type=recent`.
- Discover reads `metadata.prev_cursor` and `metadata.next_cursor`, and `wtf` is `{data:{users:[{user, token}]}}`.

## Notes

- Quoting builds the text with the format string `"@%1$s: %2$s"` with straight quotes, so the v1 quote regex in the server matches it.
- `trends` is the one request built from `base_url` instead of the 1.1 builder, so it arrives as `/1/trends/1.json`.
- Requests in old logs for `dm/user_updates`, `trends/timeline`, `dm/update_last_seen_event_id` or with `cards_platform=Android-12` came from a newer client. 4.1.9 never sends them.
